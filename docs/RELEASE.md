# Release signing — offline flow

Golden rule: **the private key never touches CI and never sits in
plaintext on disk**. A key in a GitHub secret only proves the pipeline
ran — anyone with push access could change the workflow and sign any zip.
Signing offline on the owner's machine is what makes the signature prove
*origin*.

## Pieces

| Piece | Where it lives |
|---|---|
| `release-key.dpapi` (PKCS#8 protected with DPAPI `CurrentUser`, entropy `oficinaos-release`) | `%LOCALAPPDATA%\OficinaOS\` — usable only in this Windows account on this machine |
| `oficinaos-release-key.enc.pem` backup (passphrase-encrypted PKCS#8 — PBKDF2-SHA256 ×600k + AES-256) | `E:\` or encrypted pen drive |
| Public key | Embedded in `src/OficinaDiag/Cloud/UpdateChecker.cs` (`ReleaseSigningPublicKey`) |
| `SHA256SUMS.txt` | `version <x.y.z>` + `commit <sha>` + `<hash>  <file>` — generated by `release.yml` |
| `SHA256SUMS.sig` | Base64 signature (P1363) over the SUMS — generated offline by `tools/sign-release.ps1` |

## Setup (once per machine)

```powershell
.\tools\protect-release-key.ps1
```

Asks for the current `.enc.pem` passphrase (no echo), decrypts in memory
only and writes the two artifacts above. The new backup passphrase is
asked twice — **never printed or logged; keep it in a password manager**.
At the end it verifies the public key derived from both matches the one
embedded in the updater and deletes the old loose copy.

## How a release ships

```powershell
git tag v0.4.0 && git push --tags
```

**Before tagging**: the `<Version>` of both csproj files must be `>=` the
tag version. Dev builds report it to the updater — a csproj behind the
latest release makes the updater offer "updates" that are feature
downgrades (incident #62: dev `0.3.2` offered `v0.4.0`).
`tools/version-check.mjs` fails CI if it falls behind, so the bump
usually lands in its own PR before the tag — if the tag ships without the
bump, main stays red until it enters.

1. `release.yml` runs tests, publishes self-contained, packages
   `oficinaos-diag-v<version>-win-x64.zip`, **verifies the zip contents**
   (below), writes `SHA256SUMS.txt` (`version` + `commit` + hash) and
   creates a **draft release** on GitHub. Drafts are invisible to
   `releases/latest` — the updater ignores them.
2. On the owner's machine (pwsh 7+, authenticated `gh`):

   ```powershell
   .\tools\sign-release.ps1 -Tag v0.4.0                    # DPAPI, no prompt
   .\tools\sign-release.ps1 -Tag v0.4.0 -KeyFile E:\oficinaos-release-key.enc.pem
   ```

   The script: downloads the draft's `SHA256SUMS.txt` → confirms
   `version == tag` and `commit == tag commit` → verifies the commit is
   an ancestor of `main` → asks `Sign <tag> @ <sha>? [s/N]` → signs →
   uploads the `.sig` → **publishes the draft**.

   - `-Confirm:$false` skips the question (automation).
   - `-NoPublish` tests everything but publish — the draft stays signed
     but invisible.
   - Without `.dpapi` and without `-KeyFile`, the script fails asking for
     `protect-release-key.ps1`.
3. The updater on PCs sees the published release, validates the signature
   against the embedded public key, requires `version == tag` and
   `> local version`, and only then trusts the hash and downloads the zip.

## Package-content verification

The `Verify package contents` step runs **after** packaging and **before**
the checksum and the draft. It opens the zip and fails the job with one of
three messages:

| Message | When |
|---|---|
| `Pacote em falta: <zip> não existe` | `Compress-Archive` didn't produce the file |
| `Pacote ilegível: <zip> não abre (corrompido ou truncado)` | truncated, corrupted or half-cut zip |
| `Pacote incompleto: falta <paths> no zip` | the exe, `adb`, `models.json` or the test page is missing (lists all missing ones) |

A package missing any required file is useless even if the updater accepts
it, so the failure happens before there's anything to sign.
`tools/fetch-tools.ps1` runs before publish in CI; without it, locally the
verification complains — correct behavior, not a false positive.

The path list lives in one place, `tools/package-files.txt` (one per line,
`#` comments), read by the step — no copy in the YAML. If that file is
missing the step fails with `Lista ausente: …`, so zero files are never
"verified". `PackageFilesTests` compares the list against the `Content`
entries with `CopyToPublishDirectory` of both csproj files, both ways:
flags a listed path the publish doesn't produce and a published file the
list doesn't verify, and ensures the workflow re-read the file instead of
having its own list.

On the code side the same files come from `OficinaDiag.PackagePaths`, and
`tools/build-store.ps1` reads adb from this list instead of repeating it —
changing a path in one place fails tests, not the client.

## Recovery (new PC / replaced machine)

1. Copy `oficinaos-release-key.enc.pem` from the backup (`E:\`/pen drive)
   to the new PC.
2. Run:

   ```powershell
   .\tools\protect-release-key.ps1 -SourcePem C:\path\oficinaos-release-key.enc.pem
   ```

3. Enter the backup passphrase — creates the local `.dpapi` and a new
   re-encrypted backup (you can change the passphrase here).

## Why this way

- **Compromised GitHub account** → can create drafts and tags, but without
  the key can't produce a valid `.sig` → updater refuses.
- **Malware/exposed backup** → finds `release-key.dpapi` (useless outside
  this account/machine) and `.enc.pem` (useless without the passphrase).
- **`version`+`commit` in the signed SUMS** → replay/downgrade and
  tag-moves fail validation.
- **Passphrases**: requested with `Read-Host -AsSecureString`, never in
  output, chat, logs or command-line arguments. If a passphrase ever
  appears in a log, consider it compromised and rotate the pair.

## Key rotation

```powershell
.\tools\generate-release-key.ps1   # new pair; PEM lands in the repo folder
```

1. Embed the **new public key** in the `UpdateChecker` and ship a release —
   old clients keep validating with the key they carry, so the old key
   signs *that* transition release, and from then on only the new one.
2. Run `protect-release-key.ps1` to protect the **new** pair (writes new
   `.dpapi` + backup) and retire the old files.

Note: the first key (generated 2026-10) briefly transited through a GitHub
secret during the initial implementation and was **rotated before any
release used it** — the embedded public key matches the current pair,
whose private key never left offline storage.
